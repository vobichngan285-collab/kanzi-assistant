# M02S v0.1.25 — 原厂部分导入结束状态实验（默认关闭）


## v0.1.25 是什么（独立分支，不改旧版）

真实用户上传原厂 `com.starglasses.app` APK（classes5.dex 的 `Ldp;->stopP2pWifiConnect`）明确采用：
- 成功数量为 0：`0x44/0x30/0x01`（NOT_CLEAR）；
- 成功数量等于总数：`0x44/0x30/0x00`（CLEAR，**可能删除眼镜媒体，永久禁止**）；
- 0 < 成功数量 < 总数：`0x44/0x31/<成功数量>`（FINISH_NUN）。
原厂成功完整导入时的下载记录、缩略图、文件总数与我们的只读取最新1张 JPEG 不等价。过去v0.1.20通过用户勾选发送了0x44/0x30/0x01（零下载分支），第2轮仍失败：**不能重复把它当有效修复**。公开E09协议审计称0x44/0x31/N是部分成功、不删除媒体，但当前M02S固件未验证，禁止保证无删图风险。

1. 在本APP里用户**每次启动亲自**开启复选框（默认关闭、不记忆，文本提示有丢图风险，使用可牺牲测试图）。
2. Wi-Fi由用户在实体快门拍照完成后**手动**点击“导入高清原图”开启（**绝不常连拍照**）。
3. HTTP200照片列表连续两次稳定、至少2张候选图片，**真实下载并解码成功恰好当前这一张**、BLE待机仍有效。
4. 只发一次 `0x44/0x31/0x01`，3秒内观察AA13 GATT写回执，之后释放Android NetworkCallback。**GATT成功并非固件退出证明**。
5. 结束会话时Android可能立即给出 `onLost` 或 `onUnavailable`；这时暂不调用 `stop()` 清除BLE，待完整的退出流程结束后再进入下一轮。旧NetworkCallback身份校验继续保留。
6. 没有足够图片、没有下载成功、用户未开启实验、BLE不在待机、网络失联时，**绝不发送0x44**，沿用v0.1.22安全释放手机网络的方式。

**绝不发送** `0x44/0x30/0x00` 清理帧，不发送 `0x44/0x30/0x01` 旧失败实验帧，也不发送其他 `0x44` 变体、BLE远程拍照、OTA或文件删除HTTP。 `M02sApWire.authorized()` 仍只允许原AP指令；实验指令只有自己独立、完全相等的白名单。无云上传、相册落盘、OCR/TTS、照片文本日志。

> 风险边界：公开协议的“不删除”描述不足以证明 M02S 固件永不清理文件。**务必备份所有重要眼镜照片，使用无关紧要的单张测试照片才可自行勾选**。本实验实际能否恢复第二轮Wi-Fi连接、是否出现异常副作用完全未知，不能以构建成功替代真机验证。

## 验收只看第二轮
先按实体快门拍照片A→手动导入原图A，确认0x44/0x31/01是否真正写入（以及onLost是否不关闭BLE）→眼镜实体快门再拍照片B→手动导入原图B。重点记录第二轮收到AA14 0x25的时间、Android onAvailable/onUnavailable、HTTP GET成功，以及两轮之间的BLE是否仍然待机。失败即停止，别无意义重试。

## v0.1.22 原流程（完整保留）
用户在原厂眼镜App中重复验证：实体快门拍照后原厂相册出现文件，手动点「导入」才开始连接眼镜，反复多张稳定成功；我们v0.1.18～v0.1.21把0x45拍照活动1→0与250ms后开AP绑在一起，第一张常成功，第二张常在Android精准SSID请求`onUnavailable`，甚至系统WLAN手动加入同一眼镜热点也可能失败。v0.1.20选用E09`44/30/01`实验并未稳定解决第二张；v0.1.21读取到M02S项目码`TK8`（CyanBridge T-series AP参考），被动`isImport`确实有0→1→0变化；且有一次第二张成功，也有再次失败。**还不能断言250ms自动开启是根因，必须单独隔离导入触发时机。**

## v0.1.22 流程
1. 点击 **准备蓝牙待机**。订阅AA14；不启动WLAN、不向眼镜拍照。若已经BLE待机，再点该按钮**不会强制重连**，只提示已待机。
2. **用实体快门拍照**。成功识别AA14`0x45`中的`isTakePhoto 0→1→0`，软件只标记「待导入候选」，**不**发送`0x39/0x30`，**不**自动请求Wi-Fi，**无250ms的自动延迟/触发任务**。这只是拍照结束候选，**不能在还没连眼镜HTTP之前声称已拿到真实文件列表，也不能保证JPEG已写盘**。
3. 如果眼镜确实已拍照、但缺失结束通知，用户可亲自点击 **已拍照但没收到结束通知？手动标记待导入**。这个按钮**只修改手机内存UI状态，不发送任何BLE命令**；必须由用户确认真正按快门并听到拍照反馈，避免重复读旧图。
4. 在待导入状态下，用户**单独点击** **导入高清原图（手动连接眼镜）**。这是本App**唯一**能调用`M02sApStarter.requestPhotoTransfer()`的入口；手动按钮仅调用一次准确白名单`0x39/0x30`启动T系列AP，接收AA14`0x25`准确SSID，Android只请求一次精确`WifiNetworkSpecifier`，验证真实Wi-Fi Network和私有网关，读`/app/getfilelist`合法HTTP200 JSON并复核最新文件稳定，再对最新安全候选只读GET原始JPEG到RAM显示。
5. 成功/失败均按原有流程结束本轮手机网络请求、保持BLE待机。**不会自动重试、不会自行重连或主动重新启动热点**；下一张重新按实体快门，再人工点击一次导入。连接失败时不要盲目重复点，停止并复制完整日志供比较。

保留v0.1.21已有的0x45`isImport`可选第十字段、用户点击才发的只读0x64项目查询、Android现有Wi-Fi Network数量、已有扫描缓存年龄和分阶段耗时。新增`拍照结束候选→用户点击导入`等待时间（若只有手动确认则记未知），以及连续第N轮手动导入编号。导入点击→解码耗时与以前拍照结束→解码耗时口径不同，不能直接比较认为更快。

**原 v0.1.22 安全白名单（默认关闭实验时仍适用）**：仅允许已真机成功的`AB 55 00 03 39 30 69` 开AP，以及由用户主动发起的只读项目查询`AB 55 00 02 64 64`；默认实验关闭时没有0x44结束命令、0x22遥控拍照、未知P2P、OTA、眼镜文件删除、云端上传、系统相册写入或OCR/TTS。现有照片只存手机RAM；匿名日志不记录SSID、密码、MAC、图片文件名或客户标识。
