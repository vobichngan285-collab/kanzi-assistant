# C110 passive event probe 0.1.0

User approved a standalone diagnostic after v1.0.97 lock-screen polling worked initially then camera became unresponsive and recovered after physical buttons. No production changes, no SD polling, no photo download or deletion, no HTTP or camera command, no outbound application data/heartbeat, no auto-reconnect. Only one manually started TCP connection to 192.168.1.254:3333 via unique Wi-Fi network matching gateway, max 120s and 131072 received characters; stops when leaving screen or locking, no background service. Use only after camera restored, stop immediately on abnormalities. The camera can still be affected by TCP connection, so cannot guarantee zero load. TCP handshake/ACK are inherent.

OEM static evidence reopened original APKs: SJCAM X classes5.dex LyCamera constructor 0xb520c references 3333; SocketHelper.connection 0xac714 uses TCP streams; readWork 0xac9d0 recognizes <Cmd>3020 and <Cmd>2020; LyCamera.onReadData$lambda$0 0xb6090 dispatches 3020. Zone classes5.dex LYCamera.startSocketHelper 0x18d554 references fixed address and 3333; SocketHelper.readWork 0x213148 recognizes same; LYCamera.onReadData 0x18ca00 dispatches 3020 via LyDataPack.getStatus 0x18a20c. XML Function closing tag present. Candidate status 3/4 from prior OEM audit; probe logs actual numerical statuses including others, does not assume physical shutter event. OEM X has sendPing path; this intentionally never sends ping, so no received events is inconclusive if session initialization required. No APK vendor code/assets reused.

Test: close Blue Star listener and OEM app; manual Wi-Fi connection, open independent app, start, idle 10s, press hardware shutter 3 times spaced 10s, optionally mark each in app, copy log. Stop immediately if buttons/LED become abnormal. Test physical event support first, then only after success consider integration and removal of auto-delete and periodic scan.
