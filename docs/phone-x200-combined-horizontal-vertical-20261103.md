# X200 v43 新增：自动整页方向诊断及按需旋转

- 实验包目标：`com.vobich.kanzi.x200combined`，versionCode **43**，`0.9.10-x200-combined-ab`。
- 原版、横排跨行、真竖排、综合四路 A/B **继续以相同未经旋转的帧作依据**，不更改或删除原始框。
- 自动整页方向：保守利用高可信长文本框方向判断 90°/270°；只有明显低质量且主要横向排列的文字才考虑 180°实验候选。候选一律需进行本机真实OCR第二次推理，并达到更高的文字质量门槛才能用于实时朗读。正常方向默认仅执行一遍完整OCR。
- 诊断在原始四路 A/B 之外显示自动方向候选、额外整图OCR次数与耗时、校验结果、候选正文。诊断不改正式朗读。
- **验收需真机核实**：对准同一本书的正向、左转90°、右转90°和倒置180°画面，比对是否触发、原文准确率、整图墙钟、热状态、内存及白框是否回原帧坐标。
- **仍未证明的内容**：倒置180°缺乏单纯几何特征，当前只提供极低质量保守二次测试；真竖排独立模块仍保留；这不是已经完成的准确率提升结论。
- **签名注意**：当前构建为独立 Debug APK，Android覆盖安装要求与 v42 完全相同的签名证书。CI需比较发布过的 v42 APK 与本次 v43 APK 的签名，若不一致不能声称可直接覆盖。
- 新 APK **不要求手机联网识别**，不得加入 android.permission.INTERNET，不能用语义编造、语言模型补全或移动原始识别结果。

# 看字助手 · X200 Pro 横排＋竖排综合 A/B 实验 APK

**单独安装包：** `com.vobich.kanzi.x200combined`，versionCode 42，`0.9.9-x200-combined-ab`，与正式版、旧单帧诊断版、前一个X200性能实验版均可并存。只提供 Debug APK，不是正式版更新。

## 这次真正集成了哪些实验代码？

- **原版通路（A）**：保留官方PaddleOCR v3.7.0 SDK一遍 DET+REC 的所有原识别框、原文及顺序。
- **横排跨行修复（B）**：重用上一轮真实手机价目表中已定位的三条异常狭长框 + 至少3个价格/横排锚点的`CrossRowOrientationAudit`几何警报，再由全新的`HorizontalCrossRowProposal`自动计算3–4条横向像素裁剪。通过 **PaddleOCR Android SDK内新增加的`recognizeHorizontalCandidates`**，使用**同一帧原图、同一个PP-OCRv6 Small REC**对每个裁剪真实推理，不增加整张DBNet检测。旧样本自动行中心/宽高曾在Linux得到4行16字，**但此Android APK尚待X200真机验证**，不预先承诺恢复。
- **真竖排裁剪修复（C）**：沿用第二次手机竖排介绍牌已查明的minAreaRect顶点按X错轴问题；仅极细长且上下端X不重叠、原Small识别≤3字的框，使用SDK独立Y分组透视裁剪和**第二次同Small REC**，若候选≥10字/conf≥.8才标记保守候选，**不自动替代**。
- **同帧综合候选（D）**：展示将B/C候选应用在SDK相同框序时的纯**离线诊断假设**。若B/C涉及相同原始框ID，冲突处**回退原文**。四路均独立展示原版SDK框序文本；用户可以逐行对照照片。**所有候选只出现在“设置→OCR诊断→开始OCR诊断”中**，实时扫描、TTS、白框和原始ZIP均保持原版真实OCR输出。
- **严格安全边界**：几何横排审计存在已证实的“真竖排+右侧横排价格”强反例，B和D的结果**只能人工确认**，不得因字符更多/置信度高就宣称文字必然正确。没有语义补全或云端AI，所有候选来自原帧像素 Small REC。单次手动诊断每模块额外候选上限：baseline0、balanced2、quality4、throughput4；质量模式两模块若均触发最多8次局部REC，可能耗时明显增加；实时扫描不进行这些附加实验。
- **旗舰硬件A/B**：保留X200 Pro（用户实机12GB）四档配置2线程/batch1；3线程/batch2；4线程/batch2；4线程/batch4。每档引擎重新初始化后生效；可在同一帧得到 A/B/C/D 文字结果，但不同性能档仍需重新拍摄，不能把不同帧耗时当严格逐像素同帧性能对照。
- **热/内存保护及数据**：诊断记录 baseline原始DET/REC、OCR墙钟、横排/竖排额外Small次数与耗时、Android热状态分级、可用RAM、Java/Native堆；OS内存压力或热严重时停附加REC，中热限制最多2次**每模块**。全离线，APK无INTERNET权限，无私人图片上传。
- **未完成的内容**：没有自动把B/C/D结果加入实时朗读（因为横排真竖排强误报尚未排除）；没有手机真机量到稳定p50/p95及15分钟温度；没有声称NPU/GPU EP已启用、没有保证整体CER提升；横排生成框是有根据的原型，需要更多照片的人工原文比对。

## 建议实际验收方法

1. 安装本APK（若有旧X200性能实验版，不必卸载它），选“高质量：4线程/批2”；等Small模型就绪。选择同一手机摄像头、固定距离和亮度。
2. 用旧价目表运行「设置→OCR诊断→开始OCR诊断」，查看B区是不是准确恢复4条横行，A区是不是复现之前跨行错误；再对照D组合。再用真正竖排介绍牌验证C区是否恢复以前只读1字的长列。**若输出不同，留原图进行逐字人工核验，不能靠置信度判断正确**。
3. 用真正竖排旁有横排价格的样本做负控，观察B/D是否误读，但确认**APP实时识别和朗读仍然使用原文**。相机快速移动、低光等可能使单次诊断不稳定。
4. 基线、均衡、高质量、吞吐各在**相似固定真实画面**上跑3次，记录DET、REC、横排/竖排附加时长、Android热状态与RAM。基线零附加，以便识别质量改善与性能代价清晰分离。
5. 可点击“手动采集一帧：图像＋真实裁剪＋输入张量（仅本机）”，再按“导出上次单帧诊断ZIP”；ZIP仍含原版框/原始真实张量，不被候选修改，用户自主选择是否分享。诊断文字可能涉及私密信息。

## 源码与构建审查

- 独立分支：`test/x200-combined-horizontal-vertical-ab-20261103`。
- `HorizontalCrossRowProposal.java`：仅几何生成横向3–4行候选，和`CrossRowOrientationAudit.java`原有只读判断配对；不包含用户原照片/私人字符。
- `scripts/patch_x200_shadow_sdk.py`：CI下载锁定的PaddleOCR Android v3.7.0后，按锚点安全补丁新增竖排/横排单ROI同Small REC接口；不改官方源`run(bitmap)`原始流程。
- `PaddleOcrEngine.kt`：同帧调用A的原版一次，分别触发B/C的ROI REC，诊断中生成D文本，冲突时保留原文；正式`recognizeNv21`并没有接入新候选。
- `.github/workflows/x200-combined-shadow-smoke.yml`：独立 Java 几何/回退/性能四档回归。 `.github/workflows/x200-combined-apk.yml`：独立 Android Debug 构建，严格验证无网络权限、两个Small模型哈希及包名。
