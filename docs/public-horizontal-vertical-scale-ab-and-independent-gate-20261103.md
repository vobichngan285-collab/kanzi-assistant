# 看字助手｜公开横排/竖排大批量裁剪轴向实验：双组留出验证（2026-11-03）

## 结论（先说边界）

**确定性发现：** 上游 Android SDK v3.7.0 的`minAreaRect`顶点按X排序会在某些细长倾斜的真竖排列上错误定位裁剪方向。单纯对所有风险框改用Y分组，在两组公开竖排人为剪切测试里**改善很多，但也造成17处、19处退步**，**不能作为无条件生产修复**。

**新保守方案：** 原始 Small 首次识别不超过3字，且几何确认“顶部/底部四点的X区间完全分离”，才考虑额外做**同一Small的第二次识别**；仅当第二次至少10字且平均置信度≥0.8时采用，否则保持原文。此门槛是在第一组开发数据后固定的，在**不参与选阈值的后160张图倾斜版本**的240个被抽样风险区域中，**107例实际更准确、0例更差**。这仍只是样本上的观察，不是对未来零错率的保证。候选字必须直接识别自真实图像，绝不允许基于语义补字。

本报告不声称应用已更新。**该修复尚未进入手机识别、朗读或白框通路，没有新正式APK。**

## 可复现公开数据与严格分层

1. 自然场景 **Yesianrohn/OCR-Data**（Apache-2.0）：RCTW、ReCTS、ART、CTW、MTWI，各取不在此前第0～~750位置研究中的偏移1910、2190、2470，每段20张，每种60张，**合计300张**。官方源 https://huggingface.co/datasets/Yesianrohn/OCR-Data 。
2. 竖排 **AlroWilde/vertical_annotations**（MIT）：完整 **791张公开竖排图**，`vertical_annotations.zip`中791 JPEG＋单份`metadata.jsonl`，共 **36,611个有效标注区域**。该数据含来自合成或历史版式的竖排内容，不能冒称全部来自手机实拍。源 https://huggingface.co/datasets/AlroWilde/vertical_annotations 。
3. 竖排**开发集模拟拍摄倾斜**：前160张公开竖排图，使用±0.14/±0.23的固定仿射剪切（图像与GT四点同步变换，未改变文字内容），**7,125个标注区域**，其中6,608个几何触发，采用固定随机种子reservoir抽取240个触发区域做原版/候选版 REC配对。
4. 竖排**独立留出组**：相同数据集但**不同第321–480张图**做同样剪切、**7,651个标注区域**，7,344个几何触发，reservoir另抽240个做配对，**没有用这些图来选择保守替换门槛**。两批共320张不同的公开底图，人工剪切后算320张**增强样本，不是新增320张独立自然照片**。
5. 附加本地清晰排版压力测试：10个固定中文句子×2字号×5倾斜角，共**100张人工生成图像/1,200个目标汉字**，用于识别长竖框的方向退化趋势。它不是自然照片；原版448个字符编辑错误，带几何风险护栏候选0个，40张变好、0张变差。

按**不重复的图片实例**统计：791个原版公开竖排、300个自然场景、320个基于原竖排图的仿射增强、100个本地打印体合成，共**1,511个图片实例**；独立公开底图为1,091张。**不是1511张独立手机实拍。** 按相应独立增强几何计算共约54,499个标注区域检查（竖排原图36,611只计一次），但只有受影响框会真正重新运行Small；没有用51k行的检测几何计数冒充51k行有GT的识别A/B。

## 正确的评价对象：标注文字框裁剪，而不是整页检测

- 采用公开GT polygon作为文字区域输入，对同一张源图、同一文字GT，比较**官方Android SDK v3.7.0 minAreaRect按X分组＋透视＋竖高旋转**与**只在极细长且上下两端X区间不交叠时按Y分组顶点**。
- 对同一个 ROI 都使用**同一 PP-OCRv6 Small ONNX** 权重SHA `5435fd747c9e0efe15a96d0b378d5bd157e9492ed8fd80edf08f30d02fa24634`；同一官方字典SHA `ab078671bb49f06228eadccd34f1bb501e157f7a047095ffb943ba81512c77d1`；RGB/CHW/48px、官方CTC decode；不添加AI语义纠错、模型替换、云端识别。
- **没有运行DBNet**，因此不评价先前手机价目表横排多行被误检测成竖框的缺陷；这是专门验证另一条“真正竖排列SDK裁剪错轴”的实验。图像扫描样本数量与文本识别样本数量必须严格区分。
- 人为仿射剪切、Python OpenCV模拟SDK、Linux CPU，与实际Android Camera2/USB、UVC功耗和SDK native数学可能有少量差别。
- 逐字比较NFKC小写去空格文本和原GT的Levenshtein编辑数；复杂古文标点、训练集中可能出现的非常用字会增加绝对错误率，但配对条件完全相同。

| 实际运行新旧Small REC配对 | 4 | **240** | **240** |
| 有可靠GT可评分的配对 | 1 | **240** | **240** |
| 不加保守门槛：新裁剪更准确 | 0 | **137** | **148** |
| 不加保守门槛：新裁剪更差 | 0 | **17** | **19** |

| 参考GT字符数 | 3 | 8,113 | 8,588 |

**绝不能把上表56%→13%或者61%→18%说成“软件整体识别率提升40个百分点”**：这仅针对人为倾斜下**挑出的很容易出错的风险框**，不是整页/所有检测框，更不是用户手机画面。数据内同一页有很多区域，统计单位是框，不是独立照片。

### 冻结保守门槛（做规则 → 独立验证）

事先在开发集定义：
- `original_rec_text_length <= 3` 才对这个极细长、X区间不交叠的框额外启动**第二次Small REC**；
- 候选 `candidate_text_length >= 10` 且 `candidate_confidence >= 0.8` 才采用；
- 否则一字不改地保留原始OCR结果（不受语义推断、图片旁边价格和全局竖排方向影响）。

| 固定保守策略 | 240处开发集风险框 | 240处独立留出风险框 |
|---|---:|---:|
| 原识别≤3字，真正需要第二次REC | 111 | 119 |
| 二次结果符合替换条件 | **103** | **107** |
| 被替换且编辑数改善 | **103** | **107** |
| 被替换但编辑数更差 | **0** | **0** |
| 保守替换后风险框CER（同分母） | 开发集由56.13%降至16.05%（原编辑数4,554→保守后1,302，GT共8,113字） | **60.91%→20.87%** |

开发组政策字段为依据已保存240条结果按冻结规则独立复核：共103条满足采纳条件，103条编辑数改善、0条更差。原始开发组在规则冻结前运行，因此它属于**阈值选择数据**，不能充当独立验证证据。

留出组原编辑数**5,231**，保守后**1,792**，减少**3,439**个编辑错误，GT 8,588字。无条件新裁剪编辑数**1,529**，虽然更低，但有19条变差，因此不能用无条件方案替换原文。

**关键代价：** 保守方案真正触发后的短框需要**额外一次REC**。Linux实验仅按单次识别的中位耗时，开发组约26ms，留出组约74ms/次（不同运行环境）；不能推断手机额外延迟或热负担，也不能声称无新增推理。未触发风险或原识别长度>3的普通文本不进行第二次REC。

## 透明异常和未知项

- 在独立留出组，无条件Y修复有**19条退步**，多数是本来已有较长正确串，新裁剪只改坏1个汉字/标点；因此**仅凭“候选置信度更高”并不安全**。
- 冻结门槛在2个样本各自103/107个被采纳的行上零观察退步，**不是统计意义的0误报担保**；尤其手机字体、相机角度与古籍字符分布不同。
- 自然场景4个触发框，只有1个有可用文本GT，修复前后仍同为3个编辑错误，**没有在原生态街景上证明字符改善**。
- 791张源竖排图本来都是轴对齐，风险护栏基本不触发，合成倾斜才产生大量触发，这是模拟极端方向失效的有针对性压力测试，并不代表实际用户日常触发频率。
- 每张古籍页有大量相关文字框；240框的采样是随机分层而非240张独立图，结论不能进行简单独立图显著性解释。
- **没有改动手机正式App/已有单帧诊断APK、TTS、白框、模型权重。** 本次所有数据均是公开图片/本地新创字体图，**绝不使用或上传用户私人ZIP到GitHub**。

## 实际工程决策

1. **通过：** 特定斜竖框裁剪确实是可修的，且同一Small可读回大量失字；在原版只认出极少字时，长度与置信证据共同门控能在**独立竖排增强验证集**限制误伤。
2. **不通过：** 无条件的SDK顶点排序替换。它虽总体显著改善，但开发/留出组分别出现17/19个退步，违反我们的保真目标。
3. **建议下一阶段仅在隔离Android实验版做开关**：保持原版第一次REC结果不变，仅极细长且上/下X不交叠、首次≤3字时产生第二次正确方向crop候选；在debug导出中同时记录是否采纳及新增REC耗时。手机上先比对，**正式朗读默认不替换**，直至用户真机验收。
4. **后续另一条路线**：横排跨行的DBNet误框（价目表15–17）仍需独立验证，不能用这个竖排SDK排序修复假装已解决。
