# 看字助手 OCR 智能文字行重建：第一轮真实照片对照（2026-11-03）

**阶段结论：不能把“相邻文字检测框”直接合并成大裁剪图，再让原识别模型重新读取。** 这条简单方案在开发集明显退步，在独立照片中也没有稳定收益。应继续研究原字形边缘、文字截断与异常框的诊断，而不是将几何相近直接作为合并触发。

## 研究隔离与真实模型

- 实验分支：`test/ocr-line-rebuild-ab-20261103`
- 发布基线：`release/v0.8.0-ocr-engine-rework` (#315)；**未修改任何 app/ 文件，没有新 APK。**
- 原始检测/识别输出来自此前原版模型 SHA-256 校验的 DET+REC 216 张开发照片与独立 132 张照片。
- 本轮仍由原版 PP-OCRv6 Small 的 ONNX **识别模型**逐组识别新候选裁剪图；未更换模型，也没有二次整图检测。
- 相邻框候选仅由两框坐标、分数、同一行的高度/垂直重叠/水平间距产生；不能用人工标注、OCR 结果来挑选候选。每张图最多两个候选，不引入异步帧队列。
- 基线 = 两个原始文字框的已有识别文本按横向顺序拼接，**不增加识别模型调用**。
- 试验 = 对两框的外接矩形重新裁剪，额外执行一次完整文字行识别。
- 人工标注横向同一行的字符只在**事后评价**中使用。未能可靠对齐标注的组明确排除准确率统计。
- Python/OpenCV 裁剪与 Android SDK 不完全相同；云端 CPU 计时不能代表手机 USB 摄像头+TTS 的真实延迟。

## 为什么不能直接启用

1. **几何同一行≠语义属于一个词**：价格、菜名、标志和多列菜单容易被错误拼接。
2. **原版可能已正确**：重复做一遍 OCR 可能把完整文字截断；不要为了少数漏字牺牲原本准确的文字。
3. **候选覆盖不足**：开发集仅 2 个低分候选、独立集仅 4 个涉及阈值下降后的低分框，无法修复此前发现的 51 个疑似被拆碎的文字案例。
4. **多余推理**：每个候选至少再执行一遍识别模型。开发集严格规则多出的单次识别 P95 为约 21.29ms，独立集约 23.70ms，且**只包括云端 CPU ONNX 执行，不含 USB/裁剪/TTS**。
5. **OCR 置信度不能代替正确率**：有时截字结果仍非常自信。

## 明确的下一阶段研究设计

**由“一看到相邻框就合并”转向“只修复有证据表明裁剪/分割有问题的文字”。**

下一阶段研究门控信号（先统计、不开启）：

- 分析检测框贴边墨迹/字形：笔画在裁剪边界是否连续接触，以及文字行两端是否出现截断。
- 分析相邻框与原有高分框的关系：是否真的是不同文字补充、已有文字的子框、不同菜单列，还是一整行发生过度合框。
- 只对诊断为可修复的少量候选，用源图重新裁剪、验证文字边界或局部矫正，而不是对所有同一行框再跑 OCR。
- 对每个候选坚持“原版输出 vs 新输出”的正确率、数字字符、错字/漏字、重复/错误播报风险和额外计算耗时；用新独立照片验证，不在研究集内选择最佳答案就宣称有效。
- 在不存在可靠在线选择规则时，必须保留原版识别结果，不能通过“GT 选最优”模拟应用效果。

**阶段决定：不调整 #315 检测阈值 `0.45`，不接入 SDK，不合并正式版，不生成安装包。** 用户优先事项仍是文字准确性与 UVC 摄像头稳定性。

研究代码：

- `scripts/ocr_line_rebuild_geometry.py`：可单独运行的两框同行几何规则和防误合并测试。
- `scripts/ocr_line_rebuild_real_images_ab.py`：真实原图重新裁剪、原版 OCR 对照与 GT 配对。
- `.github/workflows/ocr-line-rebuild-ab.yml`：含独立样本云端流水线（Github Actions）。
