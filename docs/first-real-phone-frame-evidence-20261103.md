# 看字助手｜首份用户手机单帧诊断数据：检测框跨横行、未见 NV21/REC 张量异常（2026-11-03）

## 本阶段状态与数据边界

用户已经主动导出并在对话中上传实验 APK 生成的 `kanzi-ocr-single-frame.zip`，本轮首次**实际读取真实手机诊断 ZIP**。下述判断来自手机原始帧、解码 PNG、24个 SDK 返回框的文字裁剪 PNG、真实 REC float32 输入及内置 metadata；**不是公开 RCTW 测试**，没有重新推理任何 OCR 模型，也没有安装/重编译新 APK。

**安全说明：用户现场拍摄的原图、原始 NV21、裁剪图、识别文字和张量均不上传到 GitHub**。本永久报告只记录匿名数值、框号、模型标识和几何结论。用户上传原件在对话附件和当前工作容器内，**不在代码仓库中**。

## 闭环核对图像与 REC 实际输入

1. **解码图像与此次 OCR 模型实际输入图片逐字节相同**：ZIP 中两个 PNG 字节完全一致，数组逐像素也完全一致；这帧没有启用自动图像增强。
2. **NV21 原始帧与图片通道转换没有显著偏差**：依据 `frame.nv21` 重建 `cv2.COLOR_YUV2RGB_NV21`，对比诊断包的 `decoded-frame.png`，约50.5%的单通道像素逐值一致，其余最多差**1个8-bit值**（均值0.495，最大1）。符合转换/舍入极小误差。**不能由此证明手机摄像头对焦一定正确**，但这帧不支持“NV21 变换严重破坏图像”的猜测。
3. **REC 字节级链路一致**：逐张读取24张裁剪 PNG，把其颜色转为 BGR，按已核实 Android SDK `RecPreprocessor` 公式进行48高度保持比例缩放、NCHW、`/127.5−1` 浮点归一化。所得 Float32 数组对照对应每份 `tensors/xxx.float32le`，**24/24形状完全一致、每个 Float32 元素都相同（最大差0）**。这是从**已经保存的裁剪图到保存的输入张量**的严格等价性，而不是 SDK 源码版本声明。
4. 用户单帧视觉观察：价目表的正常标题、服务名称和价格在原图较清晰；许多原框直接且正确地覆盖单行文字，**本样本不是整体严重失焦**。没有建立人工逐字符真值，不能据此计算整页 CER。

## 识别失准的直接证据：原本横向排列的项目被检测为纵向跨多行

这张图像里的几行服务项目是**正常从左到右的横向文字**，但由于每行内部字符间距较大、相邻行纵向间距较小，底部出现一组**跨越多个横行的竖长四边形**，SDK `QuadTextCrop` 按 `height/width≥1.5` 将其旋转90度送入 Small，结果把不同原横行的字变成了一条“串读”文本。此错误发生在**已经进入 REC 之前的文字定位及裁剪**阶段，不能仅调整 CTC 字典或 TTS 解决。

| SDK OCR结果序号（0起） | 原始长边 / 短边比（按四点源框） | 裁剪 PNG 宽×高（经过竖框旋转） | 置信度 | 人眼判定 |
|---|---:|---:|---:|---|
| **15** | 4.05 | 138×34 | 0.999893 | 含约3条横行不同字的竖向拼接 |
| **16** | 3.34 | 127×38 | 0.999784 | 同类纵向跨横行 |
| **17** | 4.28 | 168×39 | 0.999600 | 同类纵向跨横行 |

另有多只原字/碎字框（19、21、22号）在这一拥挤区域被分离显示。**这不是纯后处理白框排序问题**：进入 Small 的 SDK 真正裁剪图已经按照跨行纵框进行了透视裁剪和方向旋转；最终单行白框算法如果只处理结果绘制，无法从根本上修正 REC 的识别来源。

特别重要：15、16、17 三个不合理结果的置信度均高于 0.9996，说明**不能用高置信度当作文字/阅读行正确性的证明**，低置信重试触发器也很可能抓不到这种错误。

## 对此前多轮公开图实验的印证

- 先前配对同122区域的 CER：自动检测框16.087%，人工标注 GT 框5.797%，净差10.29个百分点。那个结果来自**公开图、受控 Linux/Python**；**本次没有真实 GT 行级标注，因此没有新的 CER 数字**。本例中跨横行的竖框给此前定位/裁剪瓶颈判断增加了**首次直接来自用户手机的视觉证据**。
- 先前官方 Android SDK 真源码裁剪/Python 数值对照12/12形状匹配、像素差≤1；本次24个真实手机裁剪 PNG → REC 真实保存张量重建全部精确匹配，因而**进一步降低**“BGR 归一化计算出错”为此例主要原因的可能性。
- 与旧的 CRAFT 阈值测试和 PP-DocLayout-S 整块版面分析无关，不能凭这一帧宣布更换模型或调整检测阈值必然改善。

## 实际下一步（不要重做已验证实验）

1. 优先在**隔离分支影子诊断**新增**方向与行归属冲突检测**：当一个竖长检测框穿过周围多条可信水平文字带（尤其固定表格行、价格行、文本基线）时，标注为“疑似跨行”，但**不擅自修改正式文字、不编造内容**；允许真实竖排文字作为反例。此项只做离线/实时轻量几何和像素检查，不重跑高开销 DET。
2. 设计并用更多真实**横行稀疏排版 vs 真竖排**样本做 A/B；只有在证据充分时再测试低开销分行裁剪补救。如果需要对同一帧的原文字局部 ROI 做第二次 REC，必须有明确的发热/延迟预算和无幻觉保真测试，不能默认开启。
3. 用户下一次可优先在**同一表格**手动保存两张帧（手持距离/角度不同、或紧密排版样本），先确认异常是否稳定重现；**先导出上一包再采下一包**，因为本工具本地只保留一份。
4. 正式 Android App、白框/朗读、Small/DBNet、TTS 和现有安装包**均未更改**；不声称已在手机上修好这一问题。

**结论：首次真机数据直接确认存在“横向文字被 DBNet 原框按纵向跨多行组合→SDK 旋转裁剪→Small 高置信读出错误组合”的链路问题。对这张图优先修定位/框方向和行归属，不应盲目换模型或改颜色通道。**
