# 看字助手｜CRAFT 768 FP32 → 静态 INT8 QDQ 量化实验结果（2026-11-03）

## 结论

**本轮实验确认量化有实际效果：模型文件减小74.8%，同机1080p连续检测耗时中位数降低约27.4%；36张公开场景测试照片的文字行匹配从149/244降至145/244，满足事先提出的145行最低准确率目标；但速度未达到事先提出的至少30%提速目标，单帧文字检测仍约967ms（未含 Small REC、相机/TTS），因此不推荐现在替换正式版或生成APK。**

完整成功 workflow：https://github.com/vobichngan285-collab/kanzi-assistant/actions/runs/41577071361

实验分支：`test/craft768-int8-qdq-vs-fp32-20261103`，只在 GitHub Actions 云端 Linux CPU 上运行；没有在真实 Android/ARM 手机上运行。使用的原版 CRAFT MLT25K ONNX SHA256 为 `28c05f8b5e97f3c5765d00bca556ec2397c86c954d4ac5ef73aa10043db16388`。

## 量化流程与模型完整性

- 静态 ONNX Runtime INT8 量化，模型仍是原版 CRAFT 的网络结构，不换骨干，不加入新的检测器；网络最大输入长边 **768**、32倍数对齐、原 RGB ImageNet 归一化与阈值/后处理固定。
- ONNX Runtime 1.21.1，`QuantFormat.QDQ`、`activation_type=QInt8`、`weight_type=QInt8`、`Conv, MatMul, Gemm`、per-channel=false，激活/权重采用对称量化；这一 S8S8 配置主要针对 ARM CPU 的候选能力，但目前真正测到的是 x86_64 Linux CPU。
- 使用9张预先选定的 DEV 照片进行校准：ART、RCTW、ReCTS各取图像编号0、1、2。**不使用 HOLDOUT 图像，也不使用人工GT框或文字标签进行量化校准**。新模型选择的 DEV/HOLDOUT 划分依然来自反复研究的72张旧公开照片，不是新的真正盲测。
- 原模型83,169,398 bytes（83.17MB，十进制），量化模型20,946,608 bytes（20.95MB），约为原尺寸25.2%，减少**74.8%**，压缩比3.971倍。
- 量化模型 SHA256：`9ab885d2f6669b77f70e9c8f68acfbe408c0b051501fd02d94bcaa0c7779ab15`。ONNX图与模型校验通过，含53个 QuantizeLinear 和107个 DequantizeLinear 算子。独立CPU会话加载、原始输出shape一致、输出均有限，6图快速验证、72图全量测试全部成功。
- 仅对内部实验过程中临时生成的模型作检验；**量化模型本体没有提交入应用、没有用于发布和生成安装包**。
- 原始输出的2张校准输入对照，平均绝对输出误差约0.001505与0.005559，最大单点绝对误差约0.290与0.157；说明量化不是逐像素等值替代，必须看最终文字框和实际输出。

## 72张公开真实场景照片，FP32/INT8都使用同一 PP-OCRv6 Small REC

比较每张图片同一套输入、同一套CRAFT阈值/后处理、同一Small REC，同一Linux runner；为减少固定顺序偏差，图片之间交替先执行FP32或INT8。GT仅用于最终评估，不用于挑框。

## 相同GitHub Linux CPU上的持续1080p检测测试

**24帧每模型，先热身2帧，按帧交替执行FP32/INT8**。相同12张公开文字照片按比例留白放入1920×1080帧，CRAFT长边768，ORT CPUExecutionProvider每会话2线程；测量CRAFT输入预处理、ONNX forward、CRAFT区域后处理，不含Small REC、NV21摄像头转换、语音首字播报。

| 1080p检测指标 | FP32 | INT8 | 变化 |
| --- | ---: | ---: | ---: |
| CRAFT整个检测P50 | 1331.23ms | **966.94ms** | **快27.4%** |
| CRAFT整个检测P95 | 1335.04ms | **970.89ms** | 快27.3% |
| 神经网络纯forward P50 | 1317.62ms | **953.54ms** | 快27.6% |
| 纯forward P95 | 1320.34ms | 957.56ms | 快27.5% |
| 模型加载耗时（同一进程依次加载） | 403.08ms | 46.41ms | 存在顺序、文件缓存、模型差异；**不可解释为安卓加载提升** |

两模型、72张照片与模拟1080p缓冲同时留在Python进程，观测混合RSS约1584MiB。这**不是单个INT8模型在Android上的PSS内存占用**，也不意味着手机需额外1.58GiB运行一个模型。

## 实际决策

1. **保留INT8 CRAFT768作为研发候选**：不是只靠理论，模型压缩与主机推理提速真实发生；并保留CRAFT相较Small的补漏优势。
2. **不直接集成正式版或生成APK**：相对原版Small仍较慢，1080p检测仍接近1秒，未测手机实际朗读响应。准确率下滑相对温和但并非零，DEV样本的代理CER上升更明显。
3. 如果要继续，建议下一阶段只做**Android ARM端量化算子兼容/ONNX Runtime实际加载和单帧推理验证**，并在取得真实设备时测Android PSS、1080p相机与TTS首字延迟、持续温升。仅编译或在x86云端运行不能算Android加载验证。
4. 对Android ARM仍可能出现加速不一致甚至变慢，不能用本轮Linux x86 CPU 27.4%作为手机提速保证。若实际设备延迟仍不可接受，保持原版Small，不应继续依赖更小的输入边长换取更严重的漏字。
5. 不继续堆Medium/视觉布局模型/新检测器；正式版保持原样。
