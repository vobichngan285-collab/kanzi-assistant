## 可视审查说明

图中**红色**为原 DBNet 框、**绿色**为本模块产生的合并候选、**蓝色**为公开 GT 文本实例/区域。蓝色**不是**经过重新人工审核的严格一行一个框 GT。可视判断以下为限度内的场景描述，不等于正式量化的逐行标注。

| 场景 | 本轮实际观察 | 对后续算法的含义 |
|---|---|---|
| RCTW-1402 | “植物医生”大字独占一行；下面“高山植物 / 纯净美肌”同一水平带、为两个蓝色 GT 实例，但已经被一个原始红框覆盖 | **一个原框对应多个 GT 实例**并不必然是跨行错误；当前模块无法/无需重复合并这个原框 |
| RCTW-1403 | 店铺横幅与下面红色 LED 字条分属不同水平行；LED 一整行可覆盖相邻多个 GT 实例 | 不能仅凭一个 DBNet 框覆盖两个 GT 就认定跨行粘连 |
| RCTW-1405 | 电线杆上不同大小的三排招聘/电话文本，原框分别保留，未产生合并 | 需保留分行隔离，不能为增加合并率强推阈值 |
| RCTW-1406 | 上方有三列**竖排**文字；底部两个原框 R3+R2 在近似相同水平带，被合成一个绿色候选，但右下还有 R0、R1 两个独立框 | 唯一合并的文字行归属仍**不确定**；不能把视觉上邻近直接等同于应合并 |
| RCTW-1409 | 倾斜店招包含大标题、小字副标题和玻璃门处若干碎字；原大框已较宽 | 不适宜用宽松阈值强合并，应该重点检查不同字号与大框遮挡 |
| RCTW-1411 | 井盖上有弧形、倾斜文字与交叠原框 | 直线单行合并策略不适合强行处理曲线文字；保守单独保留不等于有效精准识别 |

其他六张（1400、1401、1404、1407、1408、1410）已生成并观察叠画，未发生候选框合并；照片本身不足以量化“同行碎框合并收益”。

## 新的、可严格复算的几何发现：RCTW-1406

唯一绿色候选由原框 **R3 和 R2** 合并，`source_ids=[3,2]`，四边形：

```json
[260.0,402.40366, 425.0,413.0, 425.0,447.59634, 260.0,437.0]
```

除了完全覆盖源框 R3/R2 外，**还与未纳入此行的两个原框发生实质重叠**：

| 未参与合并的原始框 | 框总面积 | 与合并候选四边形的交集 | 该框被候选覆盖比例 |
|---|---:|---:|---:|
| R0 | 2000.00 px² | 740.93 px² | **37.05%** |
| R1 | 608.00 px² | 96.00 px² | **15.79%** |

计算：用之前成功产物中的**原始四点坐标**，以 OpenCV `intersectConvexConvex` 计算两凸四边形交集面积，再除以该未参与合并原框的 `contourArea`。该发现是**几何事实**，不是 GT 指标，也不需要额外 OCR 推理。

风险：如果把这种绿色候选画在正式预览上，可能与下方另一个未合并的文字框绘制出重叠、混淆的白色轮廓。**尚不能仅凭重叠断言跨行错误**；究竟哪个原框属于哪一阅读行，仍需要严格人工行级标注，尤其是 RCTW-1406 底部多条文字。

## 研发决策与风险

1. **先不修改** `LineOverlayPlanner.java` 合并阈值、原始识别文本、正式安卓覆盖层、TTS 或模型配置；**不构建 APK**。
2. 下一步若经用户批准进一步处理，可在隔离测试中先增加“候选合并轮廓对未参与行源框显著重叠”审计/保护约束与固定反例，**只用旧坐标做静态回归，不重跑模型**。保护阈值须通过更多真实样本和视觉标注检验，不能用本图反向过拟合。
3. 真正决定合并是否正确之前，仍需对 RCTW-1406 下方、双栏/竖排、曲线字和小字体样本建立可信的**严格单行**标注。公开数据集按实例分割的原 GT 不可直接冒充此标注。
4. 原像素图及叠画图保存在短期 GitHub Actions Artifact（10天）；本永久 Markdown 报告保存所有复核结果、来源、脚本/运行/产物 ID、几何和 SHA256；主分支交接文档必须追加本轮节点，保留历史。
