# 看字助手｜CRAFT 768 INT8 局部放大补漏专项实验（2026-11-03）

## 核心结论

**局部补漏“能补到真实漏字”，但目前自动触发的成本过高，收益太小；不适合马上合入默认识别流程或生成APK。** 本轮用纯GT盲选（候选选择与阈值不读人工标注）、最少用同一Small REC进行真实识别、同一帧的检测+识别总延迟、文字框去重，以及拼接整图文字编辑距离同时判断。两个方案分别跑完：

- v1「Small文字框锚点≥2 + 很小字 + 遗漏Canny边缘」，最多2个局部CRAFT：
  - 新于本研究的36张混合 ART/RCTW/ReCTS offset1100，201GT行：Small 125/201，局部125/201，新增0，完整均值 171.29→192.93ms。**仅1张图被触发，两ROI，全部边缘/重复框被滤掉。** 图集本身22张低分辨率，不能依赖此集判定密集小字补漏价值。
  - 先前研究过的36张 offset800，237GT行：Small 139，局部139，新增0，完整均值298.45→424.85ms；仅2张触发，4 ROI，零新增。
  - 结果：https://github.com/vobichngan285-collab/kanzi-assistant/actions/runs/41594455598 和 https://github.com/vobichngan285-collab/kanzi-assistant/actions/runs/41594809184
- v2「高分辨率纹理密集区 + 允许Small几乎没框时触发」，最多2个局部CRAFT；不更改Small / CRAFT / REC 权重、阈值、几何去重或文字筛选：
  - 已使用过的36张混合 offset800：Small 139/237，局部142/237，净补3行，整图简易序列编辑数445→443（少2），**额外528.46ms/图均值**；15图触发，25个局部CRAFT推理；仅3个识别后新增非空候选。
  - 预先指定的36张 RCTW offset1400（**未用作v2触发参数选择**），219GT行：Small 147/219，局部 **149/219**（+2行，0.91百分点），整图序列编辑数398→385（少13），覆盖感知CER代理32.172%→31.278%（好0.894百分点）；**完整平均357.65→1312.31ms，增加954.66ms/图、约3.67倍**，P95 585.26→2318.18ms（约3.96倍），27/36图触发、49个局部CRAFT推理，最终新增有文字候选框3个，2个新增 GT匹配行均来自Small完全零重叠的GT行；1个新增有文字候选未与GT一对一匹配，**不一定是误检**。
  - 2张有净GT新增的真实照片：RCTW索引1422（2400×3200，+1 GT，整图编辑15→11，额外1826.93ms），RCTW索引1425（2400×3200，+1 GT，整图编辑29→20，额外1843.50ms）。**其中额外耗时单图约1.8秒，是Linux runner估计，不是用户手机时延**。
  - 成功 workflow：https://github.com/vobichngan285-collab/kanzi-assistant/actions/runs/41595172085

## 技术约束、算法说明和测试可信度

- 模型固定 CRAFT MLT25K原权重量化后的 S8S8 QDQ INT8 20,946,608 bytes，SHA256 `9ab885d2f6669b77f70e9c8f68acfbe408c0b051501fd02d94bcaa0c7779ab15`。PP-OCRv6 Small DET + REC 都使用前期一致的 SHA 权重。CRAFT输入最长边768，Small检测输入最长边1600。
- Small首先正常检测+识别；局部CRAFT只在条件触发后进行。候选窗口固定格点、高分辨率Canny纹理的尚未被Small框覆盖的像素、Small检测框中心位置来评分；**完全不读人工GT标注用于触发**。v1要求≥4Small框且中位框高度小于55+较强纹理；v2仅要求原图最长边≥1280及符合已声明纹理阈值，可在Small几乎没检测到框时触发。
- 每张最多2 ROI，局部做CRAFT，再映回源图，边界裁断框拒绝。与Small或之前新框 IoU≥.30 或交叠面积占较小框≥.50 的候选拒绝；前16个通过几何过滤的CRAFT候选经同一Small REC识别，至少2个归一化文字字符才追加。这些默认阈值是 **先写死、后用CHECK评价**，不是由GET标注挑出有用的新增框。
- 使用原图颜色、长宽比，允许局部相对全图放大，**没有先装进横屏1920x1080留白**。
- 新/旧公开图均来自 `Yesianrohn/OCR-Data`，不是手机用户实拍，也非跨数据源的真正盲测。v2的CHECK集限定RCTW单数据集，不代表ART、ReCTS或世界上全部小字场景的泛化表现。
- AABB IoU≥0.4受标注粒度/拆行影响；覆盖CER代理没有对所有额外插入的字罚分；整图简单 y,x 拼接编辑距离虽计入插入，但对布局和阅读顺序非常敏感。**没有真实语音播报首字时延，也没有在Android ARM运行双模型。**
- GitHub CI成功只说明Linux CPU ONNX推理和真实公开数据上对比成功，不等同真实手机绝对耗时/温控/memory；用户之前V2405A单CRAFT推理P50在约544~665ms，并不能简单与本轮Linux合计时延相加估计安卓完整体验。

## 决策

1. 仅从算法角度：**局部CRAFT放大能救回以前Small没有发现的少量文字，方向并非完全不可行。**
2. 但当前自动触发**效率明显不合格**：36张需要额外49次CRAFT推理、每图平均近1秒才能净多2行，还产生一个无GT配对的新增有字结果；不适合所有用户默认打开，不能声称语音阅读体验提升。
3. **不生成APK、不修改正式版。** 若再研究，应先实现成本更低的「Small自身的局部ROI二次检测／低分辨率筛选」及**合理的文字行重建**，再和CRAFT局部进行同成本的比较，而不是继续提高CRAFT触发频率。或者仅把CRAFT保留为用户明确发起的“精细扫描”实验候选（必须重新单独测精度/时延后才考虑）。
4. 之前用户已完成6×24次CRAFT手机压力测试；这一轮都是云端，**不要求继续做手机高负载测试**。
