# OCR 翻页与模式切换修复（实验分支，未出安装包）

## 用户确认的两种硬性行为

**快速扫读**：第 1 页/标签仍在朗读时，不阻止下一帧 OCR；当 OCR 得到**不同文字**，立即停止前一条 TTS、清掉旧队列，然后用 `QUEUE_FLUSH` 请求朗读新文字。相同的完整文字不重复朗读；「房号201」和「房号202」即使高度相似，也属于不同内容，必须切换。

**长文阅读**：第 1 页未朗读结束期间，不执行第 2 页的自动 OCR。等全部 TTS 分段读完后，下一张不同的页面才参与 OCR，再朗读整页。不会自动用第 2 页文字打断第 1 页。用户主动“识别一次”属于显式覆盖行为。

## 代码修改

1. `ReadingModeRules.java`：两模式的 OCR 与 TTS 规则分开，避免混在一个布尔分支里。
2. `FastScanFrameGate.java`：快速扫读从原来的 30×18 场景亮度点提升到 64×36；更容易发现文本区域变化。对于原画面不变，约 2 秒才允许一次补充 OCR，防止 CPU/UVC 受到连续重复推理压力。**每次只允许一个飞行 OCR，不存帧、不排队。**
3. `MainActivity.java`：快速模式的新文字用 TTS 的 `QUEUE_FLUSH` 取代旧朗读；不再把所有文字 88% 相似当作重复。长文模式保持整页完整读完的规则。
4. 阅读模式、相机来源、自动/手动以及 OCR 模型切换时，重置帧指纹与上次 OCR 时间，丢弃旧模式的异步结果。
5. 更换 OCR 模型时，记住切换前是否处于识别中；初始化完毕后自动恢复（但手动识别仍必须由用户点击“识别一次”）。引入加载代号防止旧模型延迟回调覆盖新状态。
6. `KanziPerf` 日志记录 OCR 总墙钟时长、引擎报告时长和被语音/间隔阻挡的帧数，便于区分“翻页检测等待”与“真正 OCR 慢”。

## 已有测试与限制

纯 Java GitHub Actions 测试覆盖：快速识别第二页、长文先读完第一段、静态画面不过度重识别、比较微小文字变化、识别模式切换恢复、禁止同时多任务。

构建验收：仅 Android 编译，不生成、上传或发布 APK。

**尚未完成的真机验收**：USB 摄像头持续 1080p 时，单次 OCR 耗时、翻页到 TTS 首字的 P50/P95、TTS 真正打断延迟、摄像头 FPS/掉帧、长文不丢页，以及连续多次模式切换后无需重新打开识别开关。

注意：快速模式当前 `recognitionIntervalMs` 默认 500 ms（用户可在设置中修改），再加实际模型推理时间。不能承诺在 USB 手机上达到严格毫秒级“立即朗读”。为了稳定性，尚未启用额外二次 ONNX 识别或纯画面稳定等待策略。

## 用户在 #315 上能先检查的事项

- 按预期选择「快速扫读｜移动即读新内容」或「长文阅读｜完整读完，不打断」；
- 自动识别模式开启，而不是手动模式（手动需要点击“识别一次”）；
- 在设置中检查自动 OCR 间隔是否意外调大至数千毫秒，默认 500 ms。避免为了提速盲目改成 1 ms，因为真实推理仍受 USB/CPU 限制。
