# 看字助手｜CRAFT 720 长边（实际 704 对齐）与 768 / 640 同图对照（2026-11-03）

## 最终判断

本轮 **720 档能提速，但牺牲了 768 档的一部分文字行定位指标，依旧没有解决1080p帧检测耗时接近一秒的延迟问题，因此不应直接替换正式版。**

**为什么是 704 而非恰好720？** ONNX CRAFT 特征下采样与图像张量适合32倍数对齐。720/32=22.5；为保证有效的最长边不超过720而不向上增加计算量，设定 `CRAFT_LONG_SIDE=704`（22×32）；结果全部标为 `CRAFT720 nominal, 704 aligned`。未测试原生 tensor 宽或高为 720 的变体，也不能把这轮说成精确720网络输入。

- 工作分支：`test/craft720-vs768-vs640-20261103`
- 两个 GitHub Action Job **均成功**：https://github.com/vobichngan285-collab/kanzi-assistant/actions/runs/41575483244
- 实验只改变相同 CRAFT MLT25K ONNX 的检测输入最长边设置；模型 SHA256 `28c05f8b5e97f3c5765d00bca556ec2397c86c954d4ac5ef73aa10043db16388`，83,169,398 bytes。
- 相同 PP-OCRv6 Small REC 与原版 Small DET 权重；72 张之前已用于多轮研究的公开真实照片，同一测试程序和同一轮 CPU；没有加入 Medium 或第二套识别模型。
- 不修改任何 Android 主程序/SDK/TTS，不生成 APK。

**谨慎比较不同轮次时延**：此前不同 GitHub Actions 运行中768测到565ms全 OCR流程，本轮在本轮runner上 1476ms全 OCR流程；它们设备/负载/照片运行状态可能不同，不应直接相减。本轮自己的768/720配对更适合判断相对提速。

## 技术结论

- 如果更看重检字完整性，**768 仍是更好的候选**：HOLDOUT多识别9行，代理 CER 更低。
- 如果关注快速响应，720（704）确实提升了12~16%的Linux CPU速度，并保持相同11/42极端零重叠GT补漏，但尚不足以把检测耗时降至适合实时摄像头朗读的程度。
- 640更快，但准确率代理明显更差，不应仅盯“多匹配一行”忽略整体字符错误。
- **不推荐将720作为新默认版**，现有Small正式版保持不变。无需再盲目继续输入尺寸微调；若要真正降低延迟，下一方向应侧重移动端推理执行优化、INT8量化的验证（不能保证提速），并且需要真实Android设备测量才能做上线决定。

## 重要限制

- 72张公开自然场景照片已被反复用于选型，HOLDOUT不再是真正新盲测。
- 标注行与预测框按 AABB IoU≥0.4 一对一匹配，大框、小框、碎片拆分会导致评价歧义；并不能断言实际朗读多/少了多少字。
- 覆盖感知 CER 是代理值；漏匹配 GT 按字符全损失计，但没有把所有未匹配模型输出作为插入惩罚，**不是完整整页真实 CER**。
- 真实应用体验还涉及连续取图、语音首字响应、温升、PSS。此轮是Linux CPU，不是用户的12GB Android手机真机。
- 没有修改正式版Android程序或打包APK。
