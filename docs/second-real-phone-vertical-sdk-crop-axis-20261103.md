## 更重要的新发现：一条本来正确检测的竖排长列，SDK裁剪方向错误

使用已经存在于本地私有工作目录、与正式Android构建SHA相同的**PP-OCRv6 Small REC**：权重 `5435fd747c9e0efe15a96d0b378d5bd157e9492ed8fd80edf08f30d02fa24634`，字典YAML `ab078671bb49f06228eadccd34f1bb501e157f7a047095ffb943ba81512c77d1`，官方 SDK BGR-48高-NCHW预处理及CTC解码。

- **先复现，再修改裁剪**：直接读取用户新ZIP的全部13份 `tensors/*.float32le`，用同Small权重识别，**13/13输出和用户手机导出metadata的原文本逐字一致**，不是随意换模型的结果。
- 新样本中的真实正文竖排长列 #2、#3、#4、#5：原SDK裁剪识别分别输出 **24、25、25、21字**，置信度约0.964、0.979、0.987、0.983；若直接把这些裁剪180°翻转，结果坍缩为3、0、6、1字，说明不能统一旋转所有竖排框。
- **关键异常#12**：在源图中是**完整可见的正常长竖排列**，SDK返回的真实裁剪被错误地改变了长轴方向，原REC只输出**1个字**（置信度约0.877）；只对这条crop执行**180°旋转**，同一Small输出**24字**，且和原图该纵列视觉内容相符（置信度约0.988）。
- 独立复现官方Android SDK v3.7.0代码 `QuadTextCrop.crop` 和 `QuadGeometry.orderMinAreaRectPoints` 的OpenCV步骤，并只修顶点排序策略：对真正竖长的minAreaRect四点先按上下两端分组（Y排序），再分别按X排序，保持透视与竖框90°方向旋转规则不变。结果 **#12输出同样24字**，置信度约0.990；其它4条正常竖排列预测文本逐字不变，且原本横排被误框的旧手机样本15、16、17仍保留原输出（不把这种几何变更误称旧跨行问题已经修好）。
- 具体产生原因：上游 `QuadGeometry.orderMinAreaRectPoints` 直接先按X排序并假定最左两个点为同一“左侧边”，但在这条倾斜的细长竖排列中**顶部两个点的X坐标都比底部两个点更靠右**，先按X排序会把底部一对当作左侧边、顶部一对当右侧边，结果长轴被当作水平宽度，`QuadTextCrop`的`height/width>=1.5`垂直旋转分支失效；不是原文字真的不存在，也不是Simple模型完全无法读出。
- 这个几何“上下两对在X方向完全不交叠”的现象，在两张已提供手机诊断的共9个高度大于宽度2.6倍的长框中，**只命中第二张的#12**，旧横排跨行误框3个均未命中。是窄范围证据，不是大规模统计。
- 注意#12修复后的24字为视觉核查，不是经用户逐字标注的全页GT；不能把1→24当成对整页CER的提升，不能宣称消除了其他竖排错字、横排跨行问题或证明所有设备安全。

## 工程结论和下一步

**现在发现的是两种独立且有真实样本验证的错误机制：**

1. **原DBNet误把横排多行拼成竖框**（首张价目表的15/16/17）；通过行锚点重裁剪，本地Small在4条横行16个汉字上全部与临时人工GT吻合。但需要避免误伤真竖排，不能简单全局裁剪。
2. **竖排是真实且DBNet长框基本正确，但SDK按X排序透视顶点时把长轴方向弄错**（本张第12号）；正确Y分组裁剪使同一Small从1字变24字，无额外检测/模型替换。这个特定缺陷**更容易做小范围SDK算法修复**，且可能不需要增加每帧推理次数。

推荐先在**隔离SDK实验补丁**中只针对经几何护栏确认的极细长且上下X点集完全分离的框应用Y分组透视裁剪，保留原SDK输出做影子A/B；再用真竖排不同倾斜角和横排异常对照验证文字不倒转、耗时不增加、无原文丢失。真机安全验证通过后才可决定合并正式版。**不要现在默认改动TTS、全部竖排或全面开启180°纠正。**
