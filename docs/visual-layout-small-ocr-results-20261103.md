# 看字助手：视觉定位辅助 vs 原版 Small OCR｜真实照片专项结论（2026-11-03）

## 决策摘要

**不建议接入本轮 PP-DocLayout-S + 局部 Small DET 补检方案。** 视觉模型在正确预处理后能够覆盖大多数已标注文字行的位置，但每图平均只有约 1 个版面区域框，**不是文字行级精确框**。同照片 A/B 实验表明它没有补回任何按预先指定 IoU 规则成功匹配的标注文字行，反而增加约 33% 的 Linux CPU 处理耗时。

**值得继续投入的方向是文字行级定位与裁剪，而不是直接追加第二识别器或当前布局模型。** 同一批人工正确文字框上，原 Small REC 的独立集 CER 为 9.734%（使用 GT 做裁剪、不可上线）；这表明识别器自身仍有空间在定位更准时发挥作用，但此数字不是自动检测流程的准确率提升。

正式版、摄像头、TTS、翻页、Medium REC 均未修改；未构建 APK。

## 阶段 1：修正视觉模型的实际推理契约

测试 72 张公开自然场景文字图片，开发/独立各 36 张。起初误用了等比例 letterbox，导致开发 8.756%、独立 8.571% 的文字中心区域覆盖率。修正为该模型导出要求的**不保比例 480×480 resize、ImageNet 归一化及 scale_factor=[480/h,480/w]**后：

| 指标 | DEV | HOLDOUT |
|---|---:|---:|
| 图片数 | 36 | 36 |
| 该诊断阶段有效标注文字行 | 217 | 245 |
| 文字中心落入布局区域比率 | 92.166% | 84.898% |
| 每图布局区域框数 | 0.97 | 0.97 |
| Linux CPU 每图布局平均推理 | 37.90ms | 34.76ms |

**此覆盖率不是精确文字行检测召回率，更不是 OCR 识别率。** 大段落/页面布局区域可以包含多个文字中心点。

## 阶段 2：真正 Small OCR 同图 A/B（不调用 Medium）

相同的 72 张真实照片、完全一致的 Small DET、Small REC、BGR 模型输入、人工真值与 IoU>=0.40 一对一评估。

- A：Small DET 全图检测 + Small REC。
- B：同样的 A + PP-DocLayout-S 布局预测，选择不超过 2 个 score>=.53、面积占比 1–98% 的候选区域，按 2% padding 局部二次 Small DET，按 IoU>=.45 或较小框面积重叠>=.72 去重后补入原来列表；**只用 Small REC 识别**。规则未使用 GT 决定回检区域。

| DEV 36 图 | A 原版 | B 视觉补检 |
|---|---:|---:|
| 有效 GT 行 | 217 | 217 |
| 按 IoU 成功匹配 GT | 142 | 142 |
| 行几何匹配率 | 65.438% | 65.438% |
| 缺失 GT 字符 | 386 | 386 |
| 覆盖感知 CER 代理指标 | 42.502% | 42.502% |
| 未配对但有文字的 OCR 框数 | 43 | 44 |
| 每图平均耗时（Linux CPU） | 297.08ms | 404.15ms |

| HOLDOUT 36 图 | A 原版 | B 视觉补检 |
|---|---:|---:|
| 有效 GT 行 | 244 | 244 |
| 按 IoU 成功匹配 GT | 122 | 122 |
| 行几何匹配率 | 50.000% | 50.000% |
| 缺失 GT 字符 | 512 | 512 |
| 覆盖感知 CER 代理指标 | 51.830% | 51.830% |
| 未配对但有文字的 OCR 框数 | 57 | 59 |
| 每图平均耗时（Linux CPU） | 264.40ms | 352.78ms |

整批 72 张共 **22 次**布局指引下的局部 Small DET 复检，最终仅新增 **4 个**不重复的文字框，但成功匹配 GT 的文字行数无提升。这些未配对框可能是真文字、也可能是误框，不能直接宣称全为误检。

覆盖感知 CER 仅将未匹配 GT 文字计入漏字惩罚，同时将匹配预测的编辑距离计入错误；**未将未匹配预测的插入文字计入 CER，因此不是严格完整页面转录的 CER**。框配对的 IoU>=0.40 是代理规则，会把部分偏框或拆行框判为漏检。

## 阶段 3：用真实人工框测试 Small 识别器的上限（Oracle）

仍是同一批照片，给 Small REC 人工标注的 GT polygon 裁剪图，不运行自动 DET 或布局模型，不做 Medium。GT 只在本研究用作不可上线的理想框参考。

| 指标 | DEV | HOLDOUT |
|---|---:|---:|
| 同一批真实照片 | 36 | 36 |
| 有效标注文字行 | 217 | 244 |
| GT 字符 | 1127 | 1202 |
| Small REC 编辑距离总数 | 85 | 117 |
| **正确 GT 框下 Small REC CER** | **7.542%** | **9.734%** |
| 完全正确的标注行比例 | 77.419% | 77.459% |
| 错误/失败裁剪数 | 0 | 0 |

正确人工框结果**不能直接与上面的 51.830% 覆盖感知代理 CER 相减**：前者是标注裁剪图上的模型 CER，后者是自动框几何配对加漏检惩罚的代理指标。二者差距支持“定位与裁剪是重要瓶颈”的研究价值，但不能证明某个当前视觉模型可实现这个上限。

## 下一步技术建议

1. 不将当前 PP-DocLayout-S 局部重检测接入正式版，避免明显 CPU 开销换零已验证收益。
2. 针对真正**文字行级定位**做独立候选研究：局部放大检测、低阈值候选的图像证据判断，以及专用轻量文字行检测器；严控框膨胀导致合并两行、文字漏框和假阳性。
3. 保留同照片 A/B + GT-only Oracle 三角验证，分别报告 GT 匹配率、缺字/误读、重叠重复、数字错误、端到端耗时。候选只有在独立留出集确实改善后才推进 Android 真机验证。
4. 暂不叠加 Medium REC，不改正式 APK。Linux CPU 不等于 Android 12GB 手机速度。

**模型结论：识别器并非唯一限制；当前 PP-DocLayout-S 是区域/版面分析器，并非精确文字行画框器。**
