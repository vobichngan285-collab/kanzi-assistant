# 看字助手 | 云端 OCR 辅助稳定性 A/B 验证（2026-11-03）

**结论：研究原型确有改进，但尚不具备建议下载或并入发布版的证据。**

## 测试对象

- 当前发布基线：`release/v0.8.0-ocr-engine-rework` 的单次 OCR、`FrameChangeGate`、`PaddleOcrEngine`、`onRecognized`。
- 实验分支：`feature/ocr-selective-rescue-20261103`，`SinglePassLumaConfirmGate` 的单次 OCR + 原始 NV21 亮度稳定性辅助检查。**默认关闭、未接到 MainActivity、未生成 APK。**
- 云端环境：GitHub Actions Ubuntu / Java 17、合成亮度帧与计算预算；**没有 USB 摄像头，没有 Android 手机，也没有 TTS 真机验收**。
- 附加私有验证：先前两张真实照片在模型本地隔离环境生成平移、亮度、模糊等变换；照片**不上传至公开 GitHub**。该部分使用等价采样逻辑的 Python 参考实现，并非 Android JNI 路径。
- 新模块不运行 OCR 模型，不能改变单字准确率，更不能单靠画面一致性断言文字识别正确。

每一行 80 次固定随机种子的合成帧回放，共 13 × 80 = 1,040 组。每组对照当前基线“第一次 OCR 结果即具备朗读条件”与新研究原型“须额外确认画面稳定”。

## 单独计算耗时

GitHub 云端 CPU；每组重复 1,300 次（另有 300 次预热），单位微秒，包含候选帧亮度采样与判定、初始化；**不包含原本的 OCR 模型执行、UVC 设备驱动、预览、TextToSpeech 或 Android 系统调用。**

| 模拟场景 | P50 | P95 |
| --- | ---: | ---: |
| 完全静止 | 12.91µs | 73.78µs |
| 平移 2px | 47.98µs | 79.93µs |
| 曝光 +10 | 65.86µs | 76.10µs |
| 平移 2px + 曝光 +10 | 138.37µs | **240.51µs** |
| 不同标签 | 67.76µs | 81.83µs |

此结果不能用于承诺手机或 UVC 摄像头没有卡顿；需要设备级 P50/P95/99 与帧间隔、热量、内存指标。

## 私有原始照片派生验证

两张先前照片（书封与食品包装），各派生多种有控制的画面变换。Python 参考实现得出：
- 对原始照片分别平移 1px、2px，两张都从不接受变为可接受；
- 曝光 +10，两张都由不接受变为可接受；
- 平移 1px + 曝光 +10，两张都能接受；
- 不同照片场景，两张都拒绝；
- 3px 平移、曝光 +20，两张均拒绝；
- 微小未命中采样点的变化，两张均接受；
- 模糊场景：两张中有一张被拒绝；可能导致本应朗读的文字无法进入 `READY` 状态。

样本量极小，不应将“2/2”解释为总体 100% 成功率。

## 关于首次朗读延迟的正确比较

当前 #315 本来就是**第一次 OCR 完成后即可开始朗读**；无需再次等 2.8 秒才能首次播报。2800ms 仅是重复场景再次执行 OCR 的间隔。

新研究方案为了减少画面移动后读出旧结果，会新增约 160~180ms 的**模拟等待确认时间**，因此**并没有证明比当前 #315 首次朗读更快**。它的潜在收益是“摄像头移动时减少不合时机的旧文字播报”，但截至本实验没有真实设备测得误播报率变化。

另外，当前 `SinglePassLumaConfirmGate` 尚未连接到 `MainActivity`，所以即使代码在 GitHub 通过纯 Java 测试，也不意味着使用者下载现有包即可体验。

## 研究判断 / 发布门槛

**结论：继续保留在实验分支，暂不建议生成/下载安装包，不允许合并到 release。**

必须完成的下一项是基于真实 UVC 摄像头的采样：
- 连续取景 30~60 秒，画面保持静止、缓慢移动、轻微抖动、换标签、视角透视、不同光照；
- 对照 #315 与候选版的首次声音输出时间、重复播报次数、漏播报次数、OCR 总耗时、帧丢失、设备温升/内存及 TTS；
- 保证候选不会因为持续轻微抖动、复杂字形或误触发而降低实际可用性；
- 所有超时阈值必须在真实手机上按硬件和 USB 摄像头真实负载验证，不能以 GitHub 服务器数值代替。

用户提供了“测试确有提升才下载安装包”的要求。当前改善的是**实验模块的轻微抖动容错能力**，尚未证明软件整体体验提升；不生成 APK。
