# 看字助手｜CRAFT768 INT8 竖屏输入与 Android Java 检测框复原验证（2026-11-03）

## 结论

**第二项由开发侧完成，不需要用户承担图片算法处理。** 已在独立研究分支实现：真实相册/系统相机照片不再强制横屏1920×1080留白，保留原始方向与比例，CRAFT检测输入最长边768，对32对齐。Java端补上了 CRAFT 原文区/关联区的4连通域、抑制纯关联像素、膨胀及旋转最小矩形生成，再将候选文字框绘制为黄色轮廓；不混入正式看字助手的识别/语音管线。

**真实照片文字框后处理已在CI中验证：24项几何测试（18张ReCTS/RCTW/ART真实公开图片与6张旋转方向的几何检测）中，Python OpenCV参考产生115个文字框，Android Java算法也产生115个，按外接AABB IoU≥0.70可一对一匹配115/115；18张有GT的原始照片中，两边都匹配63行GT，0行因Java复原丢失。** 这些数字是对同一神经网络输出scoremap的 **两种后处理实现一致性**，不是全新盲测准确率/真实整页朗读准确率。

### 验证方法

- 模型：与此前x86精度和ARM64 CPU实验相同的20,946,608字节 CRAFT768 INT8 QDQ，SHA256 `9ab885d2f6669b77f70e9c8f68acfbe408c0b051501fd02d94bcaa0c7779ab15`。
- 18项自然场景原图：ART、RCTW、ReCTS各取3 DEV + 3 HOLDOUT；6项额外将已采样照片旋转90°进行方向/坐标映射专项检查（不复用未旋转GT标注）。
- 一次ONNX Runtime 1.21.1推理生成同一 `[1,H,W,2]` 文本区/关联区得分图，Python `craft_small_detector_ab.py:craft_regions` 参考解码，与 Android 项目中真实使用的 `CraftBoxDecoder.java` 在标准Java17环境编译后解码。两边完全共用同一浮点scoremap和输入宽高；没有引入另一个网络权重或额外阈值。
- 比较一对一几何匹配 IoU≥.7；GT对比继续用原来的IoU≥.4规则。全部24图运行完毕且工作流成功。
- 文字框数量：Python115、Java115、IoU≥0.70匹配115，匹配率100%；原图GT行两边各63行，Java没有相对Python新增或丢失匹配GT行。
- Java CLI启动时间（逐张约几十到一百多毫秒）只是外部JVM启动+工具开销，**不是 Android 内部文字框后处理耗时**。真实手机耗时须通过APK按钮⑨再测，但此次不要求用户完成该项。
- 图片来自旧公开数据，重复用于研发测试，不是严格新鲜HOLDOUT，不代表对所有手机图片都会100%找对真实汉字。

### Android独立测试版

- 代码 `craft768-int8-probe/app/src/main/java/com/vobich/kanzi/craftprobe/ProbeActivity.java`（保留相册或系统相机图片原朝向，长度不超过768的32倍数对齐CRAFT输入）和 `CraftBoxDecoder.java`。
- 旧版被强制填入1920×1080横屏画布，造成1536×2048照片的文字区域缩小，CRAFT实际尺寸768×448。新源码会直接缩放1536×2048纵图至约576×768，避免不必要的大面积横屏白边。
- 点击⑨只显示候选框和耗时；不做汉字转录，没有Small REC或真实TTS首字延时测试。
- 仅由用户自愿导出匿名JSON；不要求网络、不上传图片；独立包名 `com.vobich.kanzi.craftprobe`，不改正式版。
- APK CI构建通过，模型hash及 arm64-v8a JNI运行库校验通过，**但未在用户手机上真机运行这个新版**。

## 真实照片“旧版强制横屏留白 vs 新版原宽高比”的完整A/B：已完成

成功 workflow：https://github.com/vobichngan285-collab/kanzi-assistant/actions/runs/41588974116

固定同一个 CRAFT768 INT8 QDQ、同一个 Small REC、相同72张公开真实照片，每张图片比较：
- **旧方式**：先保持宽高比放进1920×1080横向白边画布，再按CRAFT长边768推理。文字区域可能大幅缩小。
- **新方式**：直接将原图片按其自身方向缩放至CRAFT最长边768（32对齐），不再插入横屏白边。
- 两种方式的预测框均映回相同原始图片坐标，并用同一 GT AABB IoU≥.4 和相同 Small REC 计算覆盖感知 CER 代理。

|---|---:|---:|
| 匹配GT文字行 | 137 | **145** |
| GT行匹配率 | 56.148% | **59.426%** |
| 漏匹配GT字符 | 469 | **396** |

DEV 36张217行：旧 115 行、新 136 行，覆盖CER代理旧51.642%、新43.035%，新法总体更完整；DEV中15张竖屏、88行：旧30行、新45行，代理旧62.579%、新43.975%。

**判断：去掉横屏留白有真实的补漏/字符覆盖收益，但不代表免费提速**。竖屏长边保持768后，实际输入像素更多，独立集均值约增加5.4%，P95延迟也明显上升；竖屏子集尤其更慢。完整低延迟扫读仍需真机评估，不能因为这项改变而直接更新默认版。

这批72图已被多轮使用，所谓HOLDOUT并非全新盲测。CER是含漏匹配GT字符惩罚的代理指标，没有计入所有不配对输出造成的插入错误，不能称为真实完整朗读错误率。Linux x86 CPU时延不等于vivo Android设备时延。该A/B仍未在新测试APK上执行相机+Small REC+TTS完整阅读。
