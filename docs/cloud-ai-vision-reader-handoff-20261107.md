## 1. 用户目标与最简操作

- **一键执行预设任务**，不需要用户说话、不需要手动输入提示词。默认操作：打开摄像头取景、选择一次任务，之后每次**点击预览**只截取**最新一帧清晰图像**，发云端视觉 AI，收到结果后直接用手机 TTS 朗读。
- 新增**盲操作/熄屏模式**：USB 外接摄像头挂在身上或指向物体、手机放入口袋，屏幕保持黑色或真正锁屏，按一下**音量加或音量减**尝试触发同一任务，自动拍照、云端理解、朗读。当前任务类型要记住，按键时无需再选。
- **真正熄屏后 USB 保持工作、应用能捕获音量键，是必须真机验证的两项硬条件，不能直接宣称已实现。** 可用屏幕黑色遮罩但保持前台/亮屏的过渡测试，不许冒充真正熄屏。

## 2. 云端模型与预设任务

- 第一批后端候选：字节跳动火山引擎/豆包**视觉模型 API**和阿里云百炼/通义千问**视觉模型 API**。用正式 API 上传图像+固定任务指令，不是调用手机里的“豆包App”或“千问App”，也不要自动操控第三方 UI。
- 先做相同照片、相同文字任务的供应商 A/B；比较正确性、文字覆盖率、阅读顺序、网络响应时间、费用和失败率。模型名称、接口、图片大小/费用以开发当天官方文档核实为准。
- **第一期 4 个任务**：
  1. **原样读文字**：按自然阅读顺序读出照片上清楚可辨的字，保留数字/价格/专名，不补字，不延伸解释。
  2. **餐厅菜单**：归类荤素、主食、汤品等，读菜名和价格；仅把菜单**明确标注**的“招牌/特色/推荐”称为招牌菜；基于判断的分类须与画面明示内容区分。
  3. **医院科室**：只优先读科室名称、楼层、诊室、指示牌和箭头；图像不清不能猜方向，不提供诊断、推荐治疗或自行推断就医科室。
  4. **商场店铺**：优先读店名、招牌、清晰的主营类别、特色及促销；跳过无关广告小字；不得把猜测当成店铺实际主营。
- **第二期候选**：商品标签（名称、价格、规格、保质期、配料、过敏原）、道路/公共指示（出口、电梯、公交、路牌）。先保证第一期质量，不堆菜单。
- 指令按任务固化于 APP/服务端，用户触发时连同图像一并发送。可按任务配置“先简短重点、再详细内容”，但**用户尚未确定具体播报先后形式**，开发时以准确完整、不啰嗦为准。
- 对云端模型制定不可省略的规则：**仅依据照片证据**；不幻觉、不脑补模糊字；看不清就直说；严格区分“画面文字”和“模型理解/推断”；没有文字时简短报告；医院、公共指引场景拒绝不确定的方向断言。系统提示词不能从根本上消除幻觉，务必实测。

## 3. 建议的精简架构（禁止一次搞太复杂）

```text
USB UVC / 手机Camera -> 原生预览或独立采集 -> 按键/点击采集1帧
                                              -> 图片尺寸/质量门限
                                              -> 用户主动授权的安全请求 -> 豆包或千问官方视觉模型
                                              -> 可校验的文字结果 -> 系统TTS语音朗读
```

- 不做连续云端视频上传、不做持续自动 OCR、不需要唤醒词；每次用户主动触发，原则上**一张图片一次请求**。新触发应取消/作废旧响应和旧朗读（递增任务序号，避免响应乱序），不能重复上传、重复念。
- USB 原生显示技术可借鉴 **1.0.9 Native Direct (RenderMode.NORMAL / TextureView)**，但不要直接在现有2.0发布分支上重写生命周期；云端路线没有持续运行本地模型的必要。
- 图像只在显式触发后发送云端；优先内存内处理，默认不留照片和OCR原文日志。具备清晰的联网/隐私提示和用户主动启用开关；失败时不静默无限重试。
- 云端需要 `INTERNET` 权限（仅新云端测试版）；现有所有离线包**不改变其离线/无INTERNET权限属性**。
- **API 密钥不得硬编码到APK、GitHub仓库、日志或安装包。** 优先最小化安全后端/代理或可审计的用户密钥配置方案；必须有调用额度上限、取消/超时、错误与费用管理。真机试验前明确图片会发送给哪家云端。
- 系统 TTS 优先沿用已验证的本机语音接口（支持用户已装语音引擎），无需额外付费云端语音服务。

## 4. 熄屏与硬件按钮难点：第一天先做可行性探针

1. **阶段A：USB单帧硬件取图**。先保证打开 USB、取图和保存/显示单帧调试结果能在 **vivo X200 Pro（Android 16，V2405A）** 工作。即使没有画面预览窗口，也要能正确完成图像读取；原1.0.9 `onPause` 会关闭 USB，不能沿用其后台行为后却假称仍在运行。
2. **阶段B：屏幕黑色但应用保持前台**。不运行本地 OCR，试验音量加/减按键事件、USB会话连续10分钟、拍一帧、手机TTS。注意屏幕全黑≠物理熄屏。
3. **阶段C：真正锁屏熄屏**。研究Android 16对前台服务、USB Host权限、持续采集、后台启动和电池优化的限制；测试按Power锁屏与长时间熄屏，必须记录摄像头有没有被系统停掉。
4. **阶段D：物理键捕获**。普通Activity的音量键KeyEvent在熄屏时**不保证被分发**。可研究用户明确授权的无障碍按键过滤或媒体按键/蓝牙遥控器方案，但遵守平台和无障碍政策；不能默默占用或屏蔽音量键、影响紧急操作或其他辅助功能。先验证再选，不强行承诺可实现。必要时提供蓝牙按钮/耳机键作为替代。
5. **阶段E：云端打通**。硬件能力稳定后再完成单帧上传→定制提示词→结果→TTS。两家API分别测；无法联网/超时应明确播报失败而非卡死。

## 5. 明天第一轮验收标准（先功能后性能）

- 采集：USB一直稳定供电/连接，前台和锁屏的状态清晰可区分；按键触发能得到**当前画面**而非上次缓存照片；设备拔插/权限拒绝/中途退出不崩溃。
- 按键：至少一种**用户认可的无屏实体键触发**路径能工作。若熄屏音量键不可用，应记录「系统限制或待定位」，不能用亮屏模拟冒充成功。
- 任务：点击/按键后只发送一次，默认不连续偷拍/上传，不保存可识别照片或敏感诊疗资料；中途重复点击取消旧请求并避免旧TTS追上新任务。
- 识别：对招牌、菜单、医院科室分别做不少于几张真实样本的A/B，逐项核对是否存在编造价格、菜单特色、科室方向；错误不得读成确定事实。
- 性能：记录每次拍照/上传/返回/朗读延迟、云端响应失败、手机温升和续航；持续 USB 观察至少10分钟；云端模型计费上限明确后才大范围测试。
- 安全与隔离：旧1.0.9、1.0.10、2.0的Git分支和APK保持原状；新应用使用独立分支、独立 applicationId；未审核完成不发布正式版。代码构建成功不等于真实硬件/云端安全验收成功。
