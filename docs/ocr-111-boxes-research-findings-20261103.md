# 看字助手 #315｜低阈值新增文字框深度研究（2026-11-03）

## 结论

**本轮没有找到可以安全接入发布版的低阈值提升策略。** 原版 PP-OCRv6 Small 的检测框阈值确为 `0.45`；直接降到 `0.35` 或 `0.30` 增加了不少候选，但绝大多数没有在目前的人工标注评估中转化成完整正确的新增识别结果。

**真正值得下一轮研究的是分割/裁剪/文本行重建**，尤其是高分框里已经有部分文字、低分框又只检测出单字或半个词的情形。发布分支与 USB 摄像头代码均未修改，无安装包。

## 研究资料和外推限制

- 研究分支：`test/ocr-111-boxes-audit-20261103`。
- 检测与识别模型均为 #315 的 SHA-256 校验原版；检测框阈值 `0.45`、像素二值阈值 `0.20`、unclip `1.40`、最长边 `1600`。
- 开发/分析集：216 张公开实景照片、1509 个人工标注区域、137 个额外候选、111 个位置未匹配区域；来自 ReCTS、RCTW、ArT。
- 独立复测集：另外 132 张从未参与筛选与调参的实景照片、864 个标注区域、90 个额外候选。
- 检测后处理及文字裁剪仍为 Python/OpenCV 对 Android SDK 的**近似复刻**，不是 Android 真机源码逐像素执行。标注采用矩形 IoU≥0.4 的代理指标，因此未匹配不等于误检；人工标注也可能不完整或分行不同。
- 识别评估只计入与标注位置匹配的新框；“完全正确”指文字与对应标注一致，并不等于整套朗读体验的准确率。
- USB 摄像头帧率、掉帧、TTS 发声和 Android 真机 OCR 延迟**未测试**。

## 发现一：111 个未知框的几何分类

| 机器几何分类 | 数量 |
| --- | ---: |
| 检测框位于标注文字的一小部分，疑似被拆碎 | **51** |
| 标注文字附近但位置不重叠 | 23 |
| 跨过多个标注区域，疑似粘连 | 7 |
| 与标注文字有少量重叠 | 6 |
| 边界对齐不一致 | 1 |
| 离已有标注文字较远 | 23 |
| **总计** | **111** |

这些是严格基于框坐标的**自动分类假设**，不是人工确认的事实。确有碎片特征，例如原标注 `VIGEN MEDICAL` 下的低分框仅输出 `MED`，标注 `PRESCRIPTION` 下的低分框仅输出 `PRESCRI`。

## 发现二：抽查真实原图，不是所有未知框都没有文字

为验证几何假设，我们额外从公开原始照片生成了带颜色标记的图像审阅板：红色为新增低分框，绿色为原始人工标注框，蓝色为 #315 原本的高分检测框。

完成了**29 个分层抽样案例**的人工目视初判：

| 目视初判（不是 OCR 正确率） | 个数 |
| --- | ---: |
| 新框位置能看见真实文字或文字片段 | **15** |
| 明显属于装饰、污渍或建筑结构等非文字 | **6** |
| 过小、过暗、背景复杂，无法可靠判定 | **8** |

具体观察：
- **真实文字片段**：ART:314 上的 `PRESCRIPTION` 被截成 `PRESCRI`；ReCTS:18 的小餐馆招牌下面确实有密集的价目文字行；ART:307 有真实 `ALL DAY` 印刷字。
- **背景误检**：RCTW:138 的墙面污迹、RCTW:157 的金属栏杆、ReCTS:112 招牌上的装饰花纹也会成为低分检测框。
- **复杂边界**：弯曲招牌、圆形标志和多行公告可能既有真实文字，也出现分行/拼框错误。

**重要：29 例是按类别故意挑选的分层样本，并非随机抽样，不得用 15/29、6/29 等比例外推整批 111 例。** 目视确认“那里有文字”也不代表 OCR 字符读对。其余未做人工目视核查的框仍保持“未确认”。

审阅板是临时研究产物，不提交原始第三方照片进代码仓库。

## 发现三：低分框与高分框大量重叠，不能简单去重

全部 137 个新框中，**42 个的面积有至少 50% 落入某个已存在的高分检测框**；62 个与原有高分框重叠面积达到自身的 10% 或以上。

如果按“只要与旧框重叠 10% 就删掉”筛选，开发集新增框从 137 减至 75，但与标注匹配且完整正确的候选也从 8 变为 3。

这意味着，重叠很可能包含“重复检测”也可能包含“原框缺失的一部分”。不能仅凭位置判断可删除性，更不能让文字只看起来不同就自动抢占朗读。

## 发现四：独立 132 张照片复测未支持调低默认阈值

| 框阈值 | 新增框（相对 0.45） | 比原版增加的匹配标注区域 |
| --- | ---: | ---: |
| `0.45`（#315 默认） | 0 | 0 |
| `0.40` | 33 | +4 |
| `0.35` | 59 | +10 |
| `0.30` | 90 | +15 |

在独立验证集里，`0.30` 新增的 90 个框中仅 **16 个框**与一处人工标注位置满足匹配条件，且其中**只有 1 个框**对应文字完全正确。其他 74 个仍是未知，而不是已证实的误检。

进一步直接复用开发集的简单筛选规则：

| 0.35 阈值下的规则 | 待处理新增框 | 与标注完全一致 |
| --- | ---: | ---: |
| 全部候选 | 59 | 1 |
| 排除自身面积与原框重叠 ≥50% | 48 | 1 |
| 排除与原框重叠 ≥10% | 36 | 0 |
| 不重叠且每图最多留 1 个 | 26 | 0 |

**筛选会减少额外 OCR 推理，也可能丢掉唯一正确恢复的文字。** 因此不能直接在正式版使用这些简单规则。

## 处理时间：只能作为云端计算参考

独立复测集用阈值 `0.35` 全部处理 59 个新框，增加识别模型调用的每张照片 P95 约 **12.04ms**；阈值 `0.30` 全部处理 90 个新框，P95 约 **17.37ms**。这不包括额外裁剪、USB、Android 驱动、TTS 及真正的用户设备争用。

即使事后将置信度低的结果丢弃，OCR 推理也已经做完了，**不会节省识别成本**。真正要降低计算量，必须在进入识别模型前控制候选框数量。

## 下一阶段最有研究价值的实验

1. **高低分框联动分析**：建立同一文本行的框邻接和相对方向关系，区分子框碎片、真正新文本、交叉行和弯曲字。
2. **对疑似截字框局部重建**：仅尝试在一行内合并相邻子框，并对照原框重识别。不要统一扩框，不能按真实标签挑选哪一版本正确。
3. **独立数据验证**：同时要求字符错误率、漏读、错误朗读和 P95 额外识别耗时改善；分开记录价格数字、房号、商品包装与书页小字。
4. **设备门槛**：只有云端证实有稳定收益才考虑 Android SDK 试验分支。USB 真机还需验收掉帧、发声时机、线程资源竞争及温升。

不启用低于 `0.45` 的默认阈值，不修改发布版、不合并、不打包 APK。
