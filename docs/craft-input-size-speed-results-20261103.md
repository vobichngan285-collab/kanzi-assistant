# 看字助手｜CRAFT 输入尺寸 960 / 768 / 640 / 512 实测（2026-11-03）

## 结果概要

**目前最有潜力的不是 FAST-T，而是在相同原版 CRAFT MLT25k ONNX 上把最大检测长边从 960 缩到 768。** 在同一 Github Actions CPU runner、相同公开真实照片、完全一致的 Small REC、固定 CRAFT 文本置信度和后处理下：

- 960：HOLDOUT 152/244 行匹配，代理 CER 38.103%，平均每图 764.42ms；
- **768：149/244 行匹配，代理 CER 40.765%，平均每图 564.52ms，较960约26.2%提速，行匹配仅少3行；**
- 640：139/244 行，代理 CER 45.507%，每图 428.54ms，较960约43.9%提速；
- 512：132/244 行，代理 CER 47.754%，每图 295.44ms，较960约61.3%提速；
- 原版 Small DET+REC：122/244 行，代理 CER 51.830%，每图 157.03ms。

**不建议当前 CRAFT 768 直接替换正式版**，因为它相对原版 Small 仍有较高 CPU 时延和83MB的模型体积；但它证明原来960的运行成本并不是保住 CRAFT 补漏能力所必需的。下一步只值得进入独立 Android 模型加载、持续内存、摄像头+TTS首字延迟性能验证，而不是未经验证构建APK。

## 与 FAST-T (MSRA512) 隔离实验对比

成功运行：https://github.com/vobichngan285-collab/kanzi-assistant/actions/runs/41571297324

此前 FAST-T MSRA512 的权重成功转成34.1MB ONNX、并通过 PyTorch/ONNX 数值一致性测试，但其独立集只有90/244行匹配、代理 CER 64.06%，每图完整平均415.30ms。**CRAFT640 单独运行**在同样照片上达到139/244行匹配、代理 CER45.507%、每图428.54ms，故即便数字速度与FAST相近，CRAFT640也是明显更值得保留的候选。**注意 FAST 与 CRAFT 分别来自不同CI运行，绝不能将415与429ms当作严格稳定同机速度比较。**

## 决策

- 若优先保住补漏效果，**CRAFT768** 是目前合理的下一阶段研究配置；
- 若优先追求低延迟，**CRAFT640** 可以作为性能档的独立候选，但匹配率与代理 CER 均显著退步；
- 512 已逼近 Small 的速度量级却牺牲大量识别指标，不是默认首选；
- CRAFT 的 ONNX 模型仍是83MB，缩图没有减少模型本身的RAM/PSS，只减少计算量；12GB内存不代表CPU性能足够。
- 先在独立非发布的安卓验证构建中检查模型能否加载、真实1080p摄像头照片的耗时和PSS/温升/持续TTS首字延迟；**未通过性能验收前不生成正式 APK**。
- 如要降低模型大小，另做 INT8 CRAFT 量化和预先固定的准确率-速度独立对照；量化可能反而降低 CPU 性能或掉字，不能推定。

## 测量局限

- 所有图片都是已用于多轮试验的公开自然场景图片，不能推广为真实手机使用者视角的严格盲测。
- 原 GT 多边形与输出框被简化为 axis-aligned bounding boxes，匹配规则 IoU>=0.40，是几何代理，不代表朗读时的真实漏字/顺序/重复问题。
- 代理 CER = 一对一匹配文字上的编辑距离 + 未匹配 GT 的字符数，没有将全部未匹配 OCR 文本计为插入字符；**不是整页真实 CER**。
- CRAFT 缩图减计算量，但可能使细字、更难照片漏检；这批照片并不是1080p手机摄像头真实分辨率专项。
- GitHub Actions Ubuntu CPU 的平均/P95不等于 Android设备时延；不包含相机取图、音频、系统负载、热节流。
- 没有修改安卓正式应用/发布分支/语音逻辑/摄像头流程，没有生成 APK。
